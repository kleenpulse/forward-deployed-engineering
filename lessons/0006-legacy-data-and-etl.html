Forward Deployed Engineering · Lesson 6 · Stage 3 · about 60 minutes

Legacy data and ETL

Finance says October doesn't add up. You get two exports of the same orders, one from a 2009 order system and one from an Excel ledger, and they disagree. This lesson loads both without losing or inventing a single row, then works out which differences are real.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

A small load-and-reconcile pipeline in Postgres. It reads a semicolon-separated Windows-1252 export and a UTF-8 Excel report, keeps every name and every cent exact, puts each bad row in a rejects table with a reason, gives the same result when you run it twice, and ends with a report of the three orders finance actually needs to look at. You'll also have a short findings note you could send to the customer.

1 · Data never arrives clean

Palantir's job ads for Forward Deployed Software Engineers list "building data pipelines and operational workflows" right next to deploying AI agents, and say FDSEs own the solution "from high-level system design and prototyping to application development and data integration".Palantir FDSE job ads on Lever, as of November 2026: ad 1 and ad 2. The agent from Lesson 5 could read one order at a time. Most AI work also needs the data in bulk: to search it, to measure the agent against it, or simply to find out whether it can be trusted.

Here is today's job. Acme's finance lead says October's numbers don't add up. You get two files:

  • orders.csv, from the order system's "Export to CSV" button. Its manual says: semicolons between fields, text in Windows-1252, dates as DD.MM.YYYY, amounts like 1.299,00.
  • ledger.csv, an Excel report from accounting, saved as CSV. One row per invoice. The "Order Ref" column is typed by hand. Dates are US style, MM/DD/YYYY, and amounts look like 1,299.00.

Finance's rule: every order that isn't cancelled should have an invoice for the same amount. Your job is to find where that isn't true, and to be sure that every difference you report is in the data, not in your code.

2 · ETL, ELT, and landing raw first

ETL is "the process of combining data from multiple sources into a large, central repository called a data warehouse": extract, transform, load. ELT "reverses the order of operations".AWS, "What is ETL?", including the section on ETL vs ELT. Google puts the difference simply: "In ELT, data is loaded into the target system in its raw format and then transformed."Google Cloud, "What is ETL?"

You'll use the ELT shape today, for three practical reasons:

  • You keep the evidence. A staging table holds each file exactly as it arrived, every column as text. When finance asks "where did this number come from?", you can show the raw row.
  • SQL is a good cleaning tool. Validating, converting and comparing whole columns is what a database does best.
  • You can rerun the transform. When you find a new problem, fix the SQL and run it again over the same raw data. You don't need to ask for a new export.

3 · Five ways a file lies

Both files open fine. The trouble is that they open fine in the wrong way too, and nothing tells you. Open them in a text editor, not in Excel, and look for these five things.

Separators and quotes

CSV has no real standard. RFC 4180 is the nearest thing, and it says so itself: "there is no formal specification in existence, which allows for a wide variety of interpretations of CSV files", and the RFC "does not specify an Internet standard of any kind". Its rules: "Fields containing line breaks (CRLF), double quotes, and commas should be enclosed in double-quotes", and a double quote inside a field is written twice.RFC 4180, section 2, rules 6 and 7, and the status section. The Postgres manual is blunter: "Many programs produce strange and occasionally perverse CSV files, so the file format is more a convention than a standard."PostgreSQL 19, COPY, "CSV Format".

The order export uses semicolons as its delimiter. One customer is "Café Lumière; Lyon", with a semicolon inside quotes. One note has a line break inside quotes. So line.split(";") cuts the customer in two, and text.split("\r\n") turns the second half of a note into a fake order. The ledger has the same problem with commas: "1,299.00". Never split CSV by hand. Use a real parser, such as Postgres's COPY.

Encoding and the BOM

A file is bytes. The character encoding is the rule that turns bytes into letters, and the file doesn't say which rule it used. In Windows-1252, ü is one byte, FC. In UTF-8 it is two, C3 BC. Decode with the wrong rule and you get mojibake:

Neither line throws an error. The second one replaces the byte it can't read with �, and the original letter is gone for good. Labels don't always help either: in the web's Encoding Standard, "“latin1” and “ascii” are just labels for windows-1252".WHATWG Encoding Standard. It adds: "Software that does not follow this standard does not always give the same answers." So ask, or read the manual, and then check a few names you know.

The ledger starts with three extra bytes, EF BB BF: a byte order mark. "An initial BOM is only used as a signature", and "some recipients of UTF-8 encoded data do not expect a BOM".Unicode, "UTF-8, UTF-16, UTF-32 & BOM" FAQ. A reader that doesn't expect it glues it to the first column name, so "Invoice No" silently becomes a different string. TextDecoder("utf-8") drops it by default. Postgres's COPY … HEADER MATCH would catch it, because the header line "must contain column names that exactly match the table's columns".PostgreSQL 19, COPY, HEADER. COPY also has an ENCODING option; in this exercise you decode in TypeScript instead.

Numbers

parseFloat("1.299,00".replace(",", ".")) returns 1.299. A thousand times too small, and no error. Even with the right digits, the type matters. Most languages, and Postgres's double precision, use binary floating point, so 0.1 + 0.2 is 0.30000000000000004. Postgres calls these types inexact: "some values cannot be converted exactly to the internal format and are stored as approximations". For money it says: "If you require exact storage and calculations (such as for monetary amounts), use the numeric type instead."PostgreSQL 19, "Floating-Point Types" and "Arbitrary Precision Numbers". Postgres also has a money type, but its output "is locale-sensitive", so loading it into a database with a different setting "might not work" ("Monetary Types"). In Postgres, 0.1::numeric + 0.2::numeric is exactly 0.3. Store amounts as numeric(12,2), and keep the currency in its own column.

Dates

The order system writes 3 October 2026 as 03.10.2026. In Bun, new Date("03.10.2026") returns 10 March 2026. That isn't a Bun bug. JavaScript only defines one date string format, adapted from ISO 8601 (2026-10-03). For anything else, "the function may fall back to any implementation-specific heuristics".ECMAScript specification, Date.parse and "Date Time String Format". The same code reads the US-style ledger correctly, so half your dates are right and half are wrong, with no error. RFC 3339 gives the reason: a date like "10/11/1996" "is completely unsuitable for global interchange because it is interpreted differently in different countries".RFC 3339, section 5.2.

Parse each source with the format it documents: to_date("OrderDate", 'DD.MM.YYYY') and to_date("Invoice Date", 'MM/DD/YYYY'). Store a date, and write 2026-10-03 whenever you show one to people.

Excel was there first

The ledger went through Excel, and Excel changes data as it opens it. It stores dates as serial numbers: "if you enter July 5, 2011, Excel converts the date to the serial number 40729". There are two date systems, and the same date is 1,462 days apart between them.Microsoft, "Date systems in Excel". The 1904 system "is the default date system in earlier versions of Excel for Mac". And "Microsoft Excel incorrectly assumes that the year 1900 is a leap year", on purpose, to stay compatible with Lotus 1-2-3.Microsoft Learn, on Excel and the year 1900. So a column of five-digit numbers in an export may be dates.

Excel also changes text that looks like something else. A 2016 study found that Excel, "when used with default settings", turned gene names such as SEPT2 into dates like "2-Sep", and that 19.6% of published papers with gene lists in Excel files had these errors.Ziemann et al., Genome Biology, 2016. In 2020 the committee that names human genes renamed the affected genes instead: "SEPT1 is now SEPTIN1".The HGNC's 2020 gene naming guidelines. That is why you open customer files in a text editor, and why order ids like A-1001 stay text.

4 · Validate, then cast. Reject, never drop

The order export has one row with the amount n/a. Cast it in SQL and the whole statement fails:

One bad row stops the load. The easy fix is worse. Since Postgres 17, COPY has an ON_ERROR option, and with ignore a bad row is discarded and the load goes on. You get "a NOTICE message … containing the count of rows that were ignored", and nothing else.PostgreSQL 19, COPY, ON_ERROR. A REJECT_LIMIT makes COPY fail after too many errors, "even with ON_ERROR set to ignore". The row with n/a is an order finance cares about. Dropping it means the totals are wrong and nobody can say why.

So do it in two steps:

  1. Validate the text. Check every column against the format the source documents, with a regular expression: an order id is ^A-[0-9]{4}$, an order amount is ^[0-9]{1,3}(\.[0-9]{3})*,[0-9]{2}$. Give each failing row one plain reason.
  2. Cast only the rows that passed. The others go to a rejects table with the source, the raw row and the reason.

Then check the sum: every input row must end up loaded, folded as an exact duplicate, or rejected. Today the order export has 13 rows after the header (12 orders and a footer line), and 10 + 1 + 2 = 13. If the sum doesn't add up, a row went missing inside your code. This is also how tools like dbt test data. A data test is a query for rows that break a rule: "If the data test returns zero failing rows, it passes". dbt ships four of them, "unique, not_null, accepted_values, and relationships".dbt docs, "Data tests". You'll write the same ideas in plain SQL.

5 · Loads you can run twice

You will run the load again: after a fix, after a new export, by accident. A load that appends rows doubles every total the second time. Two ways to make it safe:

Replace everythingUpsert
HowIn one transaction: empty the tables, load the files againINSERT … ON CONFLICT (order_id) DO UPDATE
Good forFull exports, like today'sExports that only hold new and changed rows
Watch out forVery large tablesRows deleted at the source stay in your table

Postgres says ON CONFLICT DO UPDATE "guarantees an atomic INSERT or UPDATE outcome", and that "rows proposed for insertion should not duplicate each other".PostgreSQL 19, INSERT, "ON CONFLICT Clause". Either way, give the clean table a primary key, so a duplicate fails loudly instead of slipping in. The order export lists A-1004 twice, identical in every field. Folding exact copies with select distinct is safe. Two different rows with the same id are a question for the customer, and the primary key makes sure you hear about it.

The transaction matters too. While the load runs, anyone reading the tables sees the old data or the new data, never half of each.

6 · Reconcile

Reconciliation is checking that two sources agree and listing every difference. Three decisions make it work:

  • Pick the grain. The orders file has one row per order. The ledger has one row per invoice, and an order could have two invoices. Compare at the grain both share: sum the invoices per order first.
  • Use a full outer join. An inner join only keeps orders that appear on both sides, which hides exactly the rows you're looking for. A full outer join keeps everything and fills the missing side with nulls.
  • Get the business rules from people. "Cancelled orders never get an invoice" is not in either file. Finance told you. Without it, A-1005 looks like a missing invoice.

Each order id then gets one of four verdicts: matched, amount_differs, only_in_orders or only_in_ledger. Compare on ids and amounts, not names. The ledger writes HALDEN DENTAL SUPPLY and Café Lumière, which are the same customers spelled differently, not money problems.

7 · When the data is a PDF

Sometimes the only export is a PDF report. Be careful: "a PDF file does not contain anything that resembles paragraphs, sentences or even words. When it comes to text, a PDF file is only aware of the characters and their placement."pdfminer.six docs, on converting a PDF to text. Table extractors like pdfplumber guess the table from lines "explicitly defined and/or … implied by the alignment of words on the page", and work "best on machine-generated, rather than scanned, PDFs".pdfplumber, "Extracting tables". A scanned page is a picture, and needs OCR first. So before you parse a PDF, ask whether the system that printed it can export the data behind it. Whatever you extract still goes through the same staging, validation and rejects as a CSV.

And look at what the naive report says: A-1001 has an amount difference. It doesn't. Hand that report to finance and they'll spend a day chasing a bug in your code.

Now fix start.ts. The TODO list in the file follows the order of the checks. Give yourself 30 minutes before you open the solution.

  1. Decode each file with its real encoding, then COPY it into a staging table with text columns named like the file's header.
  2. Validate in SQL before you cast. Bad rows go to rejects with a reason.
  3. Store money as numeric(12,2).
  4. Parse dates with each source's documented format.
  5. Normalize the hand-typed order refs: trim, upper case, put the hyphen back.
  6. Make the load safe to run twice: one transaction, and a primary key.
  7. Report with a full outer join, and leave cancelled orders out.

Stuck on check 1 with a COPY error about the header? With header match, the staging columns must be named exactly like the file's header, so quote them: "OrderId", "Invoice No".

9 · Fix, reject, or ask?

Each card is something you found in the two files. Decide what the pipeline should do: fix it in the transform because the right answer is documented, keep it out with a reason, or take it to the customer because only they know the answer.

10 · Check yourself

Answer from memory, then read every explanation, including the ones you got right.

11 · Write it up for finance

Acme's finance lead isn't an engineer, and they'll decide what to fix based on what you send. Write the note that goes with your report. It saves as you type.

Notice that half the note is questions. That's normal. The pipeline's job is to make the differences small, exact and believable. Deciding what they mean is the customer's job.
