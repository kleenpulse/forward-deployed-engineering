Forward Deployed Engineering · Lesson 8 · Stage 10 · about 60 minutes

Evals on customer data

Acme wants version 2 of the support agent live next week. It sounds friendlier, and it looked better in the demo. Dana, the COO, asks one question: is it at least as good as what runs today, on our own emails? This lesson builds the test that answers it with numbers, and that would have stopped v2 from promising a customer a EUR 1,299 refund nobody had approved.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

A golden set built from Acme's real emails, and a grader in TypeScript that checks what the agent did (its tool calls and the return it started) as well as what it said. It runs each case three times, reports pass@1, pass@3 and pass^3, and blocks a release that breaks a case that used to work, even when the average went up. Then you write the result for Dana in one paragraph.

1 · Why evals are part of the job

OpenAI's job ad for an FDE names three ways your work is judged: "You will measure success through production adoption, measurable workflow impact, and eval-driven feedback that changes product and model roadmaps."OpenAI, Forward Deployed Engineer (FDE) job ad, "About the role", as of November 2026. This lesson is the third one. Lesson 9 covers the other two.

An eval is a test you can run again and again: fixed inputs, an agreed idea of correct, and a score. Benchmarks from the model vendor are evals too, but they don't use your customer's data, so they can't tell Dana anything about Acme. OpenAI's eval guide lists that mistake by name: "Biased design: Creating eval datasets that don't faithfully reproduce production traffic patterns."OpenAI, "Evaluation best practices", section "Anti-patterns". The same page says "Adopt eval-driven development: Evaluate early and often." Note: OpenAI is shutting down its hosted Evals product on 30 November 2026. The advice in the guide stands; the product doesn't. Anthropic's guide says the same in four words: "Be task-specific: Design evals that mirror your real-world task distribution."Anthropic docs, "Define success criteria and build evaluations", section "Eval design principles".

Here is the situation. v1 of Acme's agent has been live for a month. It answers order-status emails and starts returns through the tools from Lesson 5 and the workflow from Lesson 7. v2 has a warmer prompt and cleans up messy order ids like a-1002 . Nobody has measured either of them.

2 · Build the golden set from the customer's data

A golden set is a list of real inputs, each with the result the customer agrees is correct. You don't need hundreds to start. Anthropic's engineers: "In reality, 20-50 simple tasks drawn from real failures is a great start", and "If you're already in production, look at your bug tracker and support queue."Anthropic, "Demystifying evals for AI agents" (January 2026), sections "Step 0. Start early" and "Step 1. Start with what you already test manually". OpenAI: "Log everything: Log as you develop so you can mine your logs for good eval cases." Acme's golden set starts with eight emails from the October helpdesk export: order-status questions, an order that doesn't exist, a small return, a big return, and a refund on a cancelled order. You'll add a case every time something goes wrong in production.

Who decides what's correct? Not you. Hamel Husain, who has built evals for many companies, starts every project by finding the principal domain expert: "In most organizations there is usually one (maybe two) key individuals whose judgment is crucial for the success of your AI product."Hamel Husain, "Using LLM-as-a-Judge For Evaluation: A Complete Guide" (October 2024), "Step 1: Find The Principal Domain Expert". At Acme that is Luis Romero's support team. They wrote down, for each email, what a correct run does. Anthropic's test for a good case: "A good task is one where two domain experts would independently reach the same pass/fail verdict." If two people on Luis's team disagree about a case, fix the case before you grade anything against it.

Expect the team to change its mind. A study of people grading model output found that "users need criteria to grade outputs, but grading outputs helps users define criteria". The authors call it criteria drift.Shankar et al., "Who Validates the Validators?" (2024), abstract. That's normal. Version the golden set like code, and write down why each change was made.

Customer data stays the customer's. The golden set is built from real emails, so it holds names, addresses and order details. Remove what the eval doesn't need (Acme's file has no customer names), keep it where your contract says Acme's data may live, and remember Lesson 4: an eval dataset built from logs can hold data some users may never see. Lesson 11 goes deeper on PII.

3 · Three kinds of grader

A grader decides whether one run passed. Anthropic's docs rank three kinds:Anthropic docs, "Define success criteria and build evaluations", section "Grade your evaluations". The engineering post's table adds that model-based graders are "Non-deterministic", "More expensive than code" and "Requires calibration with human graders for accuracy".

GraderAnthropic's verdictUse it at Acme for
Code"Fastest and most reliable, extremely scalable, but also lacks nuance"Which tools ran, with which arguments; which return exists; required and forbidden phrases
Model (an LLM judge)"Fast and flexible, scalable and suitable for complex judgment. Test to ensure reliability first, then scale."Tone with an upset customer; whether every fact in a long reply comes from a tool result
Person"Most flexible and high quality, but slow and expensive. Avoid if possible."Deciding what correct means; checking the other two graders

Anthropic's engineers sum it up: "We recommend choosing deterministic graders where possible, LLM graders where necessary or for additional flexibility, and using human graders judiciously for additional validation."Anthropic, "Demystifying evals for AI agents", "Step 5: Design graders thoughtfully". Today's grader is all code.

Whatever the grader, make it say pass or fail. Husain: "If your evaluations consist of a bunch of metrics that LLMs score on a 1-5 scale (or any other scale), you're doing it wrong."Hamel Husain, "Don't stray from binary pass/fail judgments when starting out". Nobody can act on "tone: 3.4". Everybody can act on "R-02 failed, here is the reply".

4 · Grade what it did, not only what it said

An agent's reply is a claim about what happened. The truth is in Acme's systems. Anthropic's example: "A flight-booking agent might say 'Your flight has been booked' at the end of the transcript, but the outcome is whether a reservation exists in the environment's SQL database."Anthropic, "Demystifying evals for AI agents", "The structure of an evaluation". So the outcome is the state of the real systems after the run, not the agent's words about it.

The τ-bench benchmark grades customer-service agents this way, and its example is a return. The agent "can call various (read) actions, but the agent is successful if the only database write action is" the one expected return, with the right order, items and payment method, "and the user responses contain "54.04", "41.64" as substrings."Yao et al., "τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains" (Sierra, 2024), section 3, "Reward". The abstract: it "compares the database state at the end of a conversation with the annotated goal state." That gives you two rules:

  • Reads are free. The agent may look things up in any order, as often as it likes. Only check that the reads the answer depends on happened. Anthropic warns against grading one exact path: "it's often better to grade what the agent produced, not the path it took."
  • Writes are exact. Every write must be one the golden set expects, with the right arguments, exactly once. A second start_return is a second workflow, and from Lesson 7 you know what a duplicate return costs.

OpenAI's guide names the same two checks for a single agent: "Tool selection: Evaluations that test whether the agent is able to select the correct tool to use" and "Data precision: Evaluations that verify the agent calls the tool with the correct arguments."OpenAI, "Evaluation best practices", "Single-agent architectures". Its example tool is check_order_status(order_id). The reply still matters: it is what the customer reads. So check it too, with the phrases the team gave you.

Be honest about what phrase lists can't do. τ-bench's authors say their own check "might be a necessary but not sufficient condition": the agent might, for example, "issue the return without explicit user confirmation, which violates the policy." A phrase list catches the wrong replies the team has already seen. It misses new ways of being wrong. That is what model judges and reading transcripts are for (section 7).

5 · Run every case more than once

Ask an agent the same thing three times and you may get three different runs. One good run proves little. Anthropic defines two scores for this:Anthropic, "Demystifying evals for AI agents", "How to think about non-determinism in evaluations for agents".

  • pass@k "measures the likelihood that an agent gets at least one correct solution in k attempts."
  • pass^k "measures the probability that all k trials succeed." Their example: "If your agent has a 75% per-trial success rate and you run 3 trials, the probability of passing all three is (0.75)³ ≈ 42%. This metric especially matters for customer-facing agents where users expect reliable behavior every time."

Acme's customers don't get three tries. Each email gets one run, so pass^k is the number that matches what they live through. τ-bench found the gap is large: for its best agent, "which has a >60% average task success, pass^8 drops to <25%."Yao et al., τ-bench, section 5.1, "Main results". The paper defines pass^k as "the chance that all k i.i.d. task trials are successful, averaged across tasks." pass@k is still useful while you build: if a case passes at least once, the agent can do it, and the work is to make it reliable.

6 · Regressions block the release

Anthropic separates two kinds of eval. Capability evals hold what the agent can't do well yet. Regression evals "ask, 'Does the agent still handle all the tasks it used to?' and should have a nearly 100% pass rate."Anthropic, "Demystifying evals for AI agents", "Capability vs. regression evals". For a release decision, the regression set is a release gate. The rule in today's exercise: a case that passed every run before and fails any run after is a regression, and one regression blocks the release, whatever the average does.

Why not just compare averages? Because eight cases is a tiny sample. One run more or less moves the score by four points. Evan Miller, at Anthropic, asks eval writers to treat evals as experiments and report the standard error with every score: "A 95% confidence interval can be calculated from the SEM by adding and subtracting 1.96 × SEM from the mean score."Anthropic, "A statistical approach to model evaluations" (November 2024), recommendations 1, 4 and 5. The paper: Miller, "Adding Error Bars to Evals". The same post warns: "If an eval doesn't have very many questions, confidence intervals associated with any statistical tests will tend to be wide." And when two versions answer the same questions, compare them case by case: a paired comparison "lets us eliminate the variance in question difficulty".

A per-case regression check is the simplest paired comparison there is. With eight cases you can't prove v2 is better on average. You can prove it broke R-02.

Isn't eight cases too few? Anthropic's docs say "Prioritize volume over quality: More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." Their engineers say 20 to 50 real cases is "a great start", because early changes have large effects and "small sample sizes suffice". Both are true at different times. Start small with real cases. Grow the set as the differences you care about get smaller.

7 · Check the checker

Some things code can't check: whether the tone fits a customer whose bikes arrived broken, or whether every fact in a long reply came from a tool result. For those you use a model as the judge. Judges are good but not neutral. The MT-Bench paper found strong judges reach "over 80% agreement, the same level of agreement between humans", and also "position, verbosity, and self-enhancement biases".Zheng et al., "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena" (2023), abstract. Verbosity bias is a judge preferring longer answers; position bias is preferring an answer because of where it appears. The criteria-drift study from section 2 is blunter: evaluators written by a model "simply inherit all the problems of the LLMs they evaluate, requiring further human validation."

So every automated grader, including the code you write today, gets checked against people. OpenAI: "Maintain agreement: Use human feedback to calibrate automated scoring." The exercise does exactly that: checks 1 to 5 are runs that Luis's team graded by hand, and your grader must agree with them.

Measure agreement carefully. Husain's warning: "if an error occurs in 5% of examples, a judge that always predicts Pass still has 95% agreement while detecting none of the errors."Hamel Husain, "Using LLM-as-a-Judge", FAQ "How do you validate an LLM judge against human labels?". The guide suggests reporting the judge's agreement on passes and on failures separately. Report two numbers: how many of the team's failures the judge also failed, and how many of the team's passes it also passed.

And read the transcripts. Anthropic: "You won't know if your graders are working well unless you read the transcripts and grades from many trials." When a run fails, "the transcript tells you whether the agent made a genuine mistake or whether your graders rejected a valid solution." Reading many failed transcripts and sorting the failures into groups is called error analysis, and it tells you what to grade next. Husain admits that building a judge is partly "a nice 'hack' I use to trick people into carefully looking at their data!"

8 · Shadow mode: real traffic, no real writes

A golden set is fixed. Live traffic isn't. Before v2 talks to customers, you can run it in shadow mode. AWS describes it for ML models: the new version gets "a copy of the inference requests", and "Only the responses of the production variant are returned to the calling application."AWS, "Shadow tests" (Amazon SageMaker AI docs). That page is about classic ML models, not agents.

For an agent, one more rule, and AWS's page doesn't say it for you: the shadow copy must never run a write. Give it a start_return that records what it would have done and changes nothing. Then compare: the email, what the live system or Luis's team did, and what the shadow agent wanted to do. Every disagreement is either a bug or a new golden case. This is week 3 of the plan you wrote in Lesson 2.

9 · Build it

The exercise lives in exercises/0008-evals/. Read the top of harness.ts, then open data/golden.json and a few lines of data/runs.jsonl: 48 transcripts, v1 and v2 each answering the eight emails three times. Each line holds the tool calls with their arguments and results, and the reply. start.ts is the grader most teams write first:

Read check 2. Both replies are word for word the same. The run the team failed sent amount: 666 to start_return, ten times the real refund, and no reply check can see that. Then read the scorecard: the naive grader says v2 is perfect and should ship.

Now fix start.ts. The TODO list in the file follows the order of the checks. Give yourself 30 minutes before you open the solution.

  1. Fail the run if the reply contains any must_not_say phrase.
  2. Grade the writes: every call to a tool in WRITE_TOOLS must match an expected return (same order, same amount), and every expected return must happen.
  3. Don't demand one exact sequence of calls. Extra reads are fine; a second write is not.
  4. Check that every order in lookups was read with get_order, with that exact id.
  5. Give a reason for every failure. You'll read them, and so will Luis.
  6. In summarize(), compute pass@1, pass@k and pass^k.
  7. In decide(), find regressions, and ship only if there are none and pass^k didn't go down.

10 · Which grader?

For each thing Acme wants checked, pick the cheapest grader that can check it reliably.

11 · Check yourself

Answer from memory, then read every explanation, including the ones you got right.

12 · Write the result for Dana

Dana doesn't read scorecards. Dana reads one paragraph and decides. Write the eval result for v2 from your scorecard. It saves as you type.

The hardest check is the sixth. A higher number feels like good news, and it's tempting to put it first. Lead with what the customer would have been told instead. That is the sentence Dana will remember, and it's the one that's true.
