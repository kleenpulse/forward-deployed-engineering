MCP and legacy integration

The agent needs data from a system that is older than the agent, the model and most of the team. You can't change that system. This lesson turns it into an MCP tool that speaks the protocol exactly, gives the model clean answers and useful errors, and treats the old system gently.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

An MCP server written by hand, with no SDK, that a real MCP client could start. It wraps a SOAP order system from 2009: it translates the XML and the status codes into clean fields, turns faults into errors the model can act on, waits when the rate limit says wait, gives up after three tries, and keeps its API key out of every log. You'll also be able to say, for any failure, whether to retry it or not, and why.

Here is the job for today. Acme's support agent must answer "where is my order?". The orders live in a SOAP service from 2009. Its documentation is a PDF manual. An API gateway in front of it checks an API key and allows 3 requests per second. Nobody will change it for you. Your job is the adapter between this legacy system and the agent.

The adapter will be an MCP server. MCP is the standard way to give agents tools, so one server works in any MCP client. In production you would probably use an official SDK.The SDKs are listed at modelcontextprotocol.io/docs/sdk. You'll write this one by hand anyway, because at a customer site you debug the wire: a client that won't connect, a tool that never appears, a reply that never arrives. If you know the messages, you can read what went wrong.

2 · MCP in one page

Every MCP message is JSON-RPC 2.0. There are three kinds:MCP specification 2026-07-28, "Overview", sections "Messages" and "Error Codes". The error codes come from the JSON-RPC 2.0 specification.

  • Request: id, method and params. The id "MUST NOT be null", and must not repeat an id that is still waiting for its answer.
  • Response: the same id, plus either a result or an error with an integer code and a message. Every result carries a resultType; an ordinary one is "complete".
  • Notification: a method with no id. "The receiver MUST NOT send a response."

The error codes you need today: -32700 parse error, -32601 method not found, -32602 invalid params, -32603 internal error, and one that MCP defines itself, -32022 unsupported protocol version.

MCP is stateless. "All the information needed to process a request is contained in the request itself." So every request carries a _meta object with two required fields: the protocol version (io.modelcontextprotocol/protocolVersion) and the client's capabilities (io.modelcontextprotocol/clientCapabilities). "A request missing any required field is malformed": the server answers -32602. If the server doesn't speak the requested version, it answers -32022 and lists the versions it does speak, and the client retries with one of them.MCP 2026-07-28, "Versioning and Compatibility". Servers "MUST implement" server/discover, which returns the supported versions, capabilities and server name in one call. Clients may call it first, but don't have to. Learned MCP before July 2026? The 2026-07-28 revision removed the initialize handshake and protocol-level sessions. The version and capabilities now travel on every request instead, and server/discover is new.MCP 2026-07-28, "Key Changes", major changes 1 to 3 and 8. Older clients and servers still exist. The spec calls them "legacy", and a server "MAY" support both eras. At a customer, the first thing to check when a client won't talk to your server is which revision each side speaks.

3 · stdio: one rule breaks most first servers

A local MCP server uses the stdio transport. "The client launches the MCP server as a subprocess." The rules that matter:MCP 2026-07-28, "stdio", sections on messages, shutdown and unexpected termination.

  • Messages go one per line, and "MUST NOT contain embedded newlines".
  • "The server MUST NOT write anything to its stdout that is not a valid MCP message."
  • The server "MAY write UTF-8 strings to stderr for any logging purposes".
  • The client shuts the server down by closing its input. "Servers SHOULD exit promptly when their standard input is closed."
  • If the server crashes, the client "SHOULD restart it". Because the protocol is stateless, requests in flight "are simply lost and the client can retry them against the fresh process".

The rule that bites is the second one. In Node and Bun, console.log writes to stdout. One debug line in the middle of the stream, and the client reads a line that isn't JSON-RPC. Depending on the client, you get a parse error, a dropped connection, or a tool that silently never answers. Log with console.error, which writes to stderr.

Credentials come from the environment. Lesson 3 showed that a stdio server "SHOULD NOT follow" MCP's OAuth authorization spec, and should "retrieve credentials from the environment" instead.MCP 2026-07-28, "Overview", section "Auth". So the API key arrives as an environment variable, set by whoever configured the server. Ask the Lesson 3 question: whose key is it? It is usually a service account. The key goes into one place, the request header. It never goes into a tool argument, a tool result or a log line.

4 · Design the tool for the model, not for the API

tools/list returns each tool's name, a description and an inputSchema, a JSON Schema for the arguments. A tools/call result holds content (text, for the model) and, optionally, structuredContent (JSON, for code). "A tool that returns structured content SHOULD also return the serialized JSON in a TextContent block."MCP 2026-07-28, "Tools", sections "Tool", "Tool Result" and "Structured Content". List results also carry ttlMs and cacheScope, so clients know how long they may cache the list.

The tempting design is to wrap each endpoint as it is and pass its reply straight through. Anthropic's guide to writing tools warns against exactly that: "tools that merely wrap existing software functionality or API endpoints". It gives three rules that matter here:Anthropic, "Writing effective tools for agents", sections "Choosing the right tools for agents", "Returning meaningful context from your tools" and "Prompt-engineering your tool descriptions".

  • Return meaning, not codes. Return "only high signal information" and avoid "low-level technical identifiers". Agents handle "natural language names, terms, or identifiers significantly more successfully" than cryptic ones. SHPD means nothing to a model. shipped does.
  • Describe it like you would to a new hire. Make implicit knowledge explicit: formats, terms, what the tool can't do.
  • Name arguments clearly. "Instead of a parameter named user, try a parameter named user_id."

5 · Two kinds of error

The MCP tools spec splits errors in two, and the split decides who can fix the problem:

Protocol errorTool execution error
What it meansThe request itself is brokenThe request was fine, but the tool run failed
Examples in the spec"Unknown tool", malformed requests, server errors"API failures", "Input validation errors", "Business logic errors"
On the wireA JSON-RPC error, e.g. -32602A normal result with isError: true
Who sees itClients "MAY" pass it to the modelClients "SHOULD" pass it to the model "to enable self-correction"

So a tool execution error is a message to the model. Write it so the model can act on it. Anthropic's guide asks for "specific and actionable improvements, rather than opaque error codes or tracebacks". Compare soap:Sender m:OrderNotFound with "There is no order A-9999. Check the id with the customer; ids look like A-1001." The spec also says servers "MUST" sanitize tool outputs, so a stack trace or a raw fault doesn't belong in a result either.

Reading SOAP faults. A SOAP 1.2 fault carries a code, and the two codes you'll meet tell you what to do next:W3C, SOAP 1.2 Part 1, "SOAP Fault Codes". The HTTP binding sends a Sender fault as HTTP 400 and a Receiver fault as HTTP 500 (SOAP 1.2 Part 2, Table 20).

  • Sender: "The message was incorrectly formed or did not contain the appropriate information in order to succeed." It is "an indication that the message is not to be resent without change". Return isError, and don't retry.
  • Receiver: the failure is on their side, for example an upstream system "which did not respond". "The message could succeed if resent at a later point in time." Retry, with a wait.

6 · Rate limits and retries

When the system says "later". HTTP 429 means "the user has sent too many requests in a given amount of time", and the response "MAY include a Retry-After header indicating how long to wait".RFC 6585, section 4, "429 Too Many Requests". Retry-After is "either an HTTP-date or a number of seconds", and it also comes with 503 to say how long a service "is expected to be unavailable".RFC 9110, section 10.2.3, "Retry-After". When the header is there, wait at least that long. When it isn't (a Receiver fault, a dropped connection), wait longer after each attempt.

Amazon's guide to retries gives the rest of the recipe:Amazon Builders' Library, "Timeouts, retries, and backoff with jitter".

  • Capped exponential backoff: the wait grows "exponentially after every attempt", up to a maximum.
  • Limit the attempts. Their example: a call that passes through five layers, each retrying three times, can multiply the load on a failing database by 243. Retry in one layer, and give up early.
  • Jitter: "If all the failed calls back off to the same time, they cause contention or overload again when they are retried." Add a little randomness.

Which calls are safe to retry? A call is idempotent when "the intended effect on the server of multiple identical requests" is the same as the effect of one.RFC 9110, section 9.2.2, "Idempotent Methods". Amazon's rule: "APIs with side effects aren't safe to retry unless they provide idempotency." Here SOAP sets a trap. Its HTTP binding sends every operation that isn't a simple read as a POST, so the HTTP verb tells you nothing about safety.SOAP 1.2 Part 2, section 4.1.2: when "the operation to be performed is not a retrieval", the web method "is set to "POST"". Read the manual for each operation. GetOrder only reads, so retrying it is safe. A CreateReturn that timed out may have happened anyway. Don't repeat it unless the system accepts an idempotency key; look it up first instead.

Protect the old system from the model. An agent in a loop can call a tool many times a minute. The tools spec says servers "MUST" rate limit tool invocations, and clients "SHOULD" implement timeouts for tool calls. So keep your waits short. If Retry-After asks for an hour, don't block the agent for an hour: return isError and say when to try again.

7 · When there is no API at all

Some systems only have screens. The roadmap's fallback for these is a headless browser: code that drives a real browser with no window, such as Playwright with Chromium's headless mode.Playwright docs, "Browsers", sections on Chromium's headless shell and new headless mode. Treat it as the last resort. It breaks when someone moves a button, it is slow, and it usually signs in as a real user, so the Lesson 3 questions about whose account it is come back.

Keep the same tool contract on top of it. The model calls get_order and never learns that a browser sits underneath. If a task needs several steps in one browser, MCP has no session to keep it in. The tools spec suggests returning "an explicit handle" from a first tool and passing it to the next calls, and it names "an open browser context" as an example. It also warns that "a handle is a name, not a capability": check the caller's permission on every call.MCP 2026-07-28, "Tools", section "Stateful Tools".

Look at the first and last lines together. One debug line broke the protocol and leaked the API key, because it printed the headers to stdout. In a real client, that stdout may end up in a log file that more people can read than the key's owner intended.

Now fix start.ts. The TODO list in the file follows the order of the checks. Give yourself 30 minutes before you open the solution.

  1. Log to stderr, never stdout.
  2. In handle(), check _meta before anything else: -32602 if the version or capabilities are missing, -32022 with data.supported if the version is one you don't speak.
  3. Translate the reply with pick() and STATUS_CODES into structuredContent, and return the same JSON as text.
  4. Unknown tool: -32602. Bad id format or a missing order: isError: true with one sentence the model can act on.
  5. On 429, 503 or a Receiver fault, wait and retry: Retry-After when present, otherwise doubling backoff, plus jitter.
  6. Stop after 3 attempts in total, and say to try later.
  7. Send the key only in the X-Api-Key header.

Stuck on check 5 with "retried too early"? You're probably retrying on a fixed short delay. Read the Retry-After header and wait at least that many seconds.

9 · Retry, report, or reject?

Each card is something your server might see. Decide what it should do: wait and retry, return a tool execution error (isError) without retrying, or answer with a JSON-RPC protocol error.
