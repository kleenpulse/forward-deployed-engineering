Forward Deployed Engineering · Lesson 12 · Stage 2 (specialist) · about 60 minutes

Air-gapped and VPC deployment

Your company's next customer is Torvik, which builds sonar parts for navies. Torvik wants the same agent Acme has. But its engineering network has no route to the internet: no model provider, no package downloads, no way for you to log in from your desk. Every release arrives on a disk that Ingrid, Torvik's security officer, carries across by hand. This lesson is what changes when the whole agent has to live inside someone else's walls.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

An import gate, in TypeScript and Postgres, that decides whether a release bundle carried across the gap gets installed: a signature checked against a key pinned on the inside, every file hashed, nothing unlisted, never an older version, no setting that points outside, the database migration and the version switch in one transaction, and a log the accreditor can read. Then the one-page network and release plan Torvik's security team asked for.

1 · Four places the agent can run

Until now the agent ran in your company's cloud and called a model provider over the internet. Lesson 11 kept personal data out of those calls. Some customers go further: nothing leaves at all. Job ads show where: in one analysis of 1,000 FDE ads, government and defence made up 18% of the ads that name an industry, with "air-gapped systems, FedRAMP compliance, classified environments" as the norm.Bloomberry, "I analyzed 1,000 forward deployed engineer jobs". The same figure is in the roadmap reference. Banks and hospitals ask for parts of it too. There are four common setups:

SetupWhere the model runsWhat goes outFrom your desk
Your cloud, a provider's API (Acme)At the model providerEvery request, maskedEverything
The customer's VPC, their cloud's model serviceAt the cloud provider, reached by a private endpointNothing over the internet. Read what the cloud keeps.What their cloud roles allow
The customer's VPC or data centre, their own GPUsOn their hardware (Lesson 13)Nothing, if outbound traffic is deniedThrough their VPN, if they let you

Read the last column again. Each step down the table takes a tool away from you: first the provider's dashboard, then your own logs, then your access. The work moves from "fix it in production" to "make it right before it ships, and write down how they fix it without you".

2 · A VPC: a private road to the model

The middle option is the most common one. The customer runs the agent in their own VPC, and calls the model service their cloud sells: Amazon Bedrock on AWS, the model service Google now calls Gemini Enterprise Agent Platform (formerly Vertex AI), or Microsoft Foundry on Azure. The request never touches the public internet. AWS: "You can access Amazon Bedrock as if it were in your VPC, without the use of an internet gateway, NAT device, VPN connection, or Direct Connect connection."AWS, "Use interface VPC endpoints (AWS PrivateLink) to create a private connection between your VPC and Amazon Bedrock". Also: "Instances in your VPC don't need public IP addresses to access Amazon Bedrock." Google's version lets customers reach the service with "their own internal IP addresses … without leaving their VPC networks".Google Cloud, "About accessing Gemini Enterprise Agent Platform services through Private Service Connect endpoints", updated November 2026. The old Vertex AI addresses redirect here. Microsoft's network isolation guide starts from the same need: "Major enterprises require network isolation to secure their resources from unauthorized access, tampering, or leakage of data and models."Microsoft, "How to configure network isolation for Microsoft Foundry".

Google adds a second wall. A VPC Service Controls perimeter "can help you mitigate the risk of data exfiltration", and once the service is inside one, "all public internet access to your Agent Platform instance is automatically blocked".Google Cloud, "VPC Service Controls with Gemini Enterprise Agent Platform". A private endpoint is a road in. A perimeter also stops data being copied out to a project outside it.

A private road doesn't tell you who is at the other end. That is in each service's data terms, and they differ:

  • Bedrock runs each model in AWS accounts that "Model providers don't have any access to", so "they don't have access to Amazon Bedrock logs or to customer prompts and completions".AWS, "Data protection" (Amazon Bedrock User Guide). Whether AWS keeps prompts is now a setting: "Amazon Bedrock gives you explicit control over whether the prompts and outputs from your inference requests are retained", and where it does, "AWS may retain the data for safety and abuse-prevention purposes. The model provider does not receive it."AWS, "Data retention" (Amazon Bedrock User Guide), checked November 2026.
  • Microsoft Foundry, for the models Azure sells: prompts and completions "are NOT available to OpenAI or other providers of Models sold by Azure".Microsoft, "Data, privacy, and security for Foundry Models sold by Azure in Microsoft Foundry". But Claude in Foundry comes in two hosting options, and in one of them inference runs on an "Anthropic-operated service running on Anthropic infrastructure". Even in the Azure-hosted option, "Operational data that contains no prompts or completions is stored on Anthropic's systems outside Azure."Anthropic, "Claude in Microsoft Foundry", checked November 2026. Its examples of that operational data: "safety classifier scores, identifiers, and usage and billing data".

So "it's in our Azure" or "it's in our AWS" is where the conversation starts, not where it ends. For each setup, find the page that says where inference runs and what is kept, quote it with the date you read it, and put it in front of the customer's security team. These pages change: Bedrock's retention setting is newer than many of the security reviews that cite Bedrock.

3 · Default deny, then find what calls out

A VPC doesn't stop traffic going out by itself. Two defaults catch people:

  • A "private" subnet can still reach the internet. AWS: "You can use a NAT gateway so that instances in a private subnet can connect to services outside your VPC but external services can't initiate a connection with those instances."AWS, "NAT gateways" (Amazon VPC User Guide). Private means nobody can call in. It says nothing about calling out.
  • Containers may call anywhere. Kubernetes: "By default, a pod is non-isolated for egress; all outbound connections are allowed."Kubernetes, "Network Policies", including "Default deny all egress traffic".

Regulated customers write the fix down as a rule. The US government's catalogue of security controls says: "Deny network communications traffic by default and allow network communications traffic by exception", so that "only those system connections that are essential and approved are allowed".NIST, SP 800-53 Rev. 5.1.1, control SC-7(5), "Deny by Default — Allow by Exception", and its discussion. It is in the Moderate and High baselines. Your agent is one more system on the customer's network, so each of its connections needs a place on that approved list.

In Kubernetes, the starting point is a policy that "selects all pods but does not allow any egress traffic from those pods". Then you add back, one by one, the places the agent may reach: the model server, the CRM, the internal collector for traces. The same page has a catch: "A default deny-all egress policy also blocks DNS traffic." So the first rule you add back is DNS, to the customer's own resolver.

Then find what calls out. Run the agent in a test copy of the customer's network with egress denied, and read what was blocked. On AWS, VPC Flow Logs "capture information about the IP traffic going to and from network interfaces in your VPC".AWS, "Logging IP traffic using VPC Flow Logs". Every blocked attempt is a default someone chose, and the list is usually longer than the team expects. Two documented examples:

  • Model libraries download at runtime. Hugging Face Transformers: "When you load a pretrained model with from_pretrained(), the model is downloaded from the Hub and locally cached." Even with the file cached, a download call "still triggers a HTTP request to check that a new version is not available". Set HF_HUB_OFFLINE=1: "If set, no HTTP calls will be made to the Hugging Face Hub."Hugging Face, Transformers "Installation", "Offline mode", and huggingface_hub "Environment variables", HF_HUB_OFFLINE.
  • Telemetry goes where its settings say. OpenTelemetry's default endpoint is local, http://localhost:4318 for HTTP.OpenTelemetry, "OTLP Exporter Configuration", OTEL_EXPORTER_OTLP_ENDPOINT. Your own product's defaults are the ones to check: a crash reporter or usage counter that sends to your company's cloud works at Acme, and is a blocked connection, or a leak, at Torvik.

Fix each one in the build, not with an exception in the firewall: bake the model and every package into the image, point telemetry at the customer's collector, turn update checks off. Write the final list of allowed destinations into the plan, with a reason for each.

4 · Air-gapped: nothing crosses by itself

An air gap is stricter than "egress denied". NIST's definition: "An interface between two systems at which (a) they are not connected physically and (b) any logical connection is not automated (i.e., data is transferred through the interface only manually, under human control)."NIST CSRC glossary, "air gap", from CNSSI 4009 and RFC 4949. Torvik's staff call the connected network the low side and the closed one the high side. Data crosses in two ways. By hand, on approved media, as Ingrid does. Or through a cross domain solution, "a form of controlled interface that provides the ability to manually and/or automatically access and transfer information between different security domains", which is often built on a data diode, a device "that allows data to travel only in one direction".NIST CSRC glossary, "cross domain solution (CDS)" and "data diode". One direction means your releases can go in, and the logs don't come back out to you.

Where the model runs. There is no provider API on the high side. That leaves two options:

  • An open-weight model on the customer's own GPUs. The weights arrive on the media like any other file. Choosing and serving one is Lesson 13.
  • A cloud built for classified work, if the customer's government accredits one. In the US, AWS describes its Top Secret Region as "the first air-gapped commercial cloud"; Microsoft offers "dedicated US air-gapped regions" for Secret and Top Secret data; and Google Distributed Cloud air-gapped "is built to remain disconnected in perpetuity", with Gemini generally available on it since August 2025.AWS, "Announcing the New AWS Secret Region"; Microsoft, "Azure for US Government"; Google Cloud, "Google Distributed Cloud air-gapped" and "Run Gemini anywhere" (28 August 2025). Anthropic says its Claude Gov models "are already deployed by agencies at the highest level of U.S. national security", with access "limited to those who operate in such classified environments".Anthropic, "Claude Gov models for U.S. national security customers" (6 June 2025). Earlier, Palantir announced Claude "hosted on Palantir's Impact Level 6 (IL6) accredited environment" (November 2024). IL6 "is reserved for the storage and processing of information classified up to the SECRET level" (Microsoft Learn). These are US programmes. Torvik is European, so its security team, not you, says which of them, if any, it may use.

What disappears for you. Everything you did from your desk in Lessons 2 to 11 needs a new answer:

5 · Carrying a release across

A disk that arrives on the high side is a download from an untrusted mirror: you know what it should hold, but not what it does. The Update Framework (TUF), a specification for secure software updates, lists the attacks an updater must stop. Four of them map straight onto a disk in Ingrid's hand:The Update Framework Specification, version 1.0.37, section 1.5.2, "Goals to protect against specific attacks".

TUF's attackIn its wordsOn Ingrid's disk
Arbitrary installation"an attacker cannot provide arbitrary files in response to download requests"A release signed by someone else; a script added to the disk after signing
Rollback attack"An attacker cannot trick clients into installing software that is older than that which the client previously knew to be available."Last September's genuine release, found on an old stick
Mix-and-match"a combination of metadata that never existed together on the repository at the same time"This month's image with last month's model file
Indefinite freeze"the same, outdated metadata without the client being aware of the problem"No disk arrives at all, and the high side runs an old version with a known bug

The first three are stopped by one design. The vendor signs a manifest: a list of every file with its SHA-256 hash and size, plus the version. The high side checks the digital signature, then checks every file against the list, and refuses anything the list doesn't name. Then it compares the version with the one running. The fourth can't be stopped in code: an air gap is a freeze by design. The plan has to say how often releases cross, and how an urgent security fix jumps the queue.

The key is the whole game. A signature only proves that someone holding a private key signed it. Which key? TUF: "The client-side of the framework MUST ship with trusted root keys", and it assumes "a good, trusted copy of this file was shipped with the package manager or software updater using an out-of-band process".TUF specification, sections 2.1.1 "Root role" and 5.2 "Load trusted root metadata". At Torvik, that out-of-band process is the accreditation: the vendor's public key was installed on the high side once, and Ingrid's team compared its fingerprint with the vendor in person. That pinned key is the only one that counts. A key that travels on the same disk as the release proves nothing, because whoever made the disk chose it. And there is no key server to ask: the high side has no network.

A valid signature says who built it, not that it's safe here. The vendor's own build can still contain a telemetry endpoint pointing at the vendor's cloud, or a database migration that fails. So the gate also checks what the release will do: every URL in its configuration must stay inside Torvik's network, and the migrations and the version switch happen in one transaction, so a failure leaves the old version running untouched.

You won't build this gate from scratch in a real deployment. Zarf, an open-source tool for air gaps, lets you "package the parts of the internet your app needs into a single compressed file to be installed without connectivity", and can "Create and verify package signatures with cosign"."What is Zarf?", Zarf documentation. Sigstore's cosign verifies "with an on-disk public key provided by the signer": cosign verify --key cosign.pub.Sigstore, "Verifying Signatures". But you have to know what such a tool checks, because Torvik's accreditor will ask you, and some customers will want their own checks on top. Building one is the fastest way to know.

6 · Build it

The exercise lives in exercises/0012-air-gap/. The top of harness.ts describes a bundle, the key pinned on the high side, the deployment and schema_migrations tables, and the import_log. The harness writes nine bundles to exercises/0012-air-gap/media/ on every run, one for each disk Ingrid carries across in December. Open a few before you start. You write one function: importBundle(dir).

start.ts is the import script most teams write first. It checks a signature, so it feels safe:

Read what got in. A model file with a changed byte. A shell script nobody signed. A release signed by a stranger, accepted because the stranger packed their own key. Last September's version, put back in place over this month's. A build that sends traces to the vendor's cloud. And nine attempts to reach a key server, each one an alert on Ingrid's screen. The signature check worked every time. It just checked the wrong things.

Fix start.ts. The TODO list in the file follows the checks. Give yourself 35 minutes before you open the solution.

  1. Migrations, their records and the version switch in one db.transaction. A failure changes nothing.
  2. Hash every listed file, and check its size. One mismatch refuses the bundle.
  3. Refuse unlisted files (apart from the three envelope files) and missing ones.
  4. Verify manifest.sig with PINNED_KEY before you trust the manifest. No network, no key from the bundle.
  5. Only a newer version, compared part by part as numbers.
  6. Every URL in config.json, however deep, must have a host inside torvik.internal.
  7. One import_log row per call, with the manifest's hash and, for a refusal, the reason.

The full solution is in solution.ts. Two small functions carry two of the traps:

Semantic Versioning says it plainly: "Major, minor, and patch versions are always compared numerically."Semantic Versioning 2.0.0, item 11, on precedence. As strings, "1.10.0" < "1.9.2", because "1" sorts before "9". And the second function checks the host, because the vendor's crash reporter lives at https://crashes.vendor.example/tenants/torvik.internal/report: a check that looks for "torvik.internal" anywhere in the URL waves it through.

Three installs, six refusals, and every refusal says what to send next. The vendor can match each hash in the log against its own release record without ever seeing the high side.

Try three experiments in a copy of solution.ts. Replace compareVersions(manifest.version, running.version) <= 0 with manifest.version <= running.version: 1.10.0 is refused as "older" than 1.9.2, nothing installs, and four checks fail. Undo that, and make inside() return url.includes(INSIDE): only check 6 fails, because the crash reporter's URL gets through. Undo that too, and replace db.transaction(async (tx) => { … }) with a plain function called on db: only check 1 fails. Migration 0005 stays in place after 0006 breaks, and the next install has to work around half a release.

7 · On the list, or fixed in the build?

You ran the agent in a test copy of Torvik's network with all egress denied, and read what tried to get out. Each card is one connection. Decide whether it goes on the allowed list, or gets fixed in the build so it never tries again.

8 · Check yourself

Answer from memory, then read every explanation, including the ones you got right.

9 · Write Torvik's plan

Torvik's security team won't approve the agent until they have a network and release plan they can check line by line. Write it for them: people who read firewall rules all day, but don't know your product. It saves as you type.

The first check matters most. Torvik's team will compare your list with what their firewall sees. If something tries to get out that isn't on your list, they stop trusting the rest of the page.
