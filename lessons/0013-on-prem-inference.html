Edge and on-prem inference

In Lesson 12, Torvik's release gate let a file called weights.bin onto the high side. Now someone has to run it. There is no model provider behind the agent any more: just one server in Torvik's machine room, two GPUs, and Mats, the engineer who looks after them. This lesson is the work a provider used to do for you: choosing the model, fitting it in memory, serving it, and proving it's still good enough.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

A sizing and acceptance script, in TypeScript, that picks which of four versions of an open-weight model Torvik runs. It does the memory sums for weights and KV cache on Torvik's two GPUs, writes the exact vllm serve command with nothing left to defaults, and refuses any version that got a single golden-set case wrong or is too slow at the busiest hour. Then the one-page sizing memo Mats and Ingrid sign off.

1 · Four jobs the provider used to do

When the agent called a model provider's API, four questions had answers before you asked them. On Torvik's high side, they're yours:

QuestionWith a providerOn Torvik's GPUs
May we use this model for this work?The provider's terms, signed onceEach model's own licence (section 2)
Does it fit?Not your problemWeights plus KV cache, in the GPUs Torvik owns (section 3)
How is it served?An API that already worksA model server you configure, flag by flag (section 4)
Is it still good?The provider tests its own modelsYour golden set, on the exact version you'll run (section 5)

The roadmap calls this stage "edge and on-prem" because the same questions come in two sizes. On-prem is Torvik's case: a server in a customer's machine room, serving many people. Edge is a device near the work, such as a laptop on a ship with no connection. For that size the usual tool is llama.cpp, whose "main goal … is to enable LLM (and MLLM) inference with minimal setup and state-of-the-art performance on a wide range of hardware - locally and in the cloud". It "requires the model to be stored in the GGUF file format".llama.cpp README and docs/models.md, checked November 2026. Ollama, built on it, describes itself as a way to "Start building with open models. Access the latest releases locally or in the cloud with complete privacy" (Ollama README). The questions are the same on a laptop, and the numbers are just smaller. Today uses the bigger size, with vLLM, an open-source model server built for GPUs and many users.

2 · Open weights, but not open for every use

"Open-weight" means you can download the weights. It doesn't mean you may use them for anything. Torvik builds sonar parts for navies, so the first filter isn't technical.

  • Some licences forbid defence work. Meta's acceptable use policy for Llama 4 forbids uses "that present a risk of death or bodily harm to individuals, including use of Llama 4 related to the following: a. Military, warfare, nuclear industries or applications, espionage, use for materials or activities that are subject to the International Traffic Arms Regulations (ITAR)".Meta, "Llama 4 Acceptable Use Policy", section 2, checked November 2026. llama.com now redirects to dev.meta.ai, and llama.com/use-policy shows the older Llama 2 policy. Read the one for the model you'd run.
  • Exceptions live in blog posts, not in the licence. In November 2024 Meta said it was "making Llama available to U.S. government agencies, including those that are working on defense and national security applications, and private sector partners supporting their work". In September 2025 it extended this to the Five Eyes partners and to "France, Germany, Italy, Japan, and South Korea, as well as NATO and European Union institutions".Meta, "Open Source AI Can Help America Lead in AI and Strengthen Global Security" (4 November 2024) and "Strengthening US National Security by Making Llama Available to Key Allies" (23 September 2025). Torvik is a Norwegian company. Norway isn't on that list, and a company that supplies navies isn't a NATO institution. The policy text still says "Military, warfare". That is a question for Torvik's lawyers and Meta, in writing, not for you.
  • Many strong models use Apache 2.0. Qwen3, the Apache-licensed Mistral Small models, OpenAI's gpt-oss and Google's Gemma 4 all say license: apache-2.0 on their model cards. Older Gemma models stay on Google's own Gemma Terms.Model cards: Qwen3-32B, Mistral Small 3.2, gpt-oss-120b. Google, "Gemma Terms of Use" (last modified 1 April 2026): "For Gemma 4 terms, see the Gemma 4 license", which links to Apache 2.0. The licence grants "a perpetual, worldwide, non-exclusive, no-charge, royalty-free, irrevocable copyright license to reproduce, prepare Derivative Works of, publicly display, publicly perform, sublicense, and distribute the Work", with no list of forbidden uses.Apache License, Version 2.0, section 2. Section 3 grants patents in similar words.

Two more things belong in the same conversation. A licence isn't the only rule: export controls and Torvik's contracts apply too. And the law around AI may not work the way you'd guess. The EU AI Act "does not apply to AI systems where and in so far they are placed on the market, put into service, or used with or without modification exclusively for military, defence or national security purposes".Regulation (EU) 2024/1689 (the AI Act), Article 2(3). Norway is outside the EU but in the EEA. Whether and when the Act applies there is another question for Torvik's lawyers. Note the word "exclusively". A support agent that also helps Torvik's civilian customers may not be exclusive. Your job is to bring these questions up early, with the model card and the licence text in hand, and to write down who answered them.

Torvik's lawyers cleared one family: Skerry, an Apache 2.0 model. (Skerry is made up for this course. It's shaped like Qwen3-32B, so its numbers are realistic.) Four versions of it crossed the gap in Lesson 12's bundles.

3 · Will it fit? Weights, then the KV cache

NVIDIA's guide to inference names "the two main contributors to the GPU LLM memory requirement": "model weights and the KV cache".NVIDIA Technical Blog, "Mastering LLM Techniques: Inference Optimization" (17 November 2023).

Weights are the easy part: parameters times bytes per parameter. NVIDIA's example: "a model with 7 billion parameters (such as Llama 2 7B), loaded in 16-bit precision (FP16 or BF16) would take roughly 7B * sizeof(FP16) ~= 14 GB in memory." A 32-billion-parameter model in BF16 needs about 64 GB, in FP8 about half, and in INT4 about a quarter, plus some extra for the numbers that undo the scaling.

The KV cache is the part teams forget. For every token of every request in progress, each layer keeps a key and a value, so the model doesn't recompute the whole conversation for each new word. NVIDIA's formula: "Size of KV cache per token in bytes = 2 * (num_layers) * (num_heads * dim_head) * precision_in_bytes". It grows "linearly with batch size and sequence length". One detail changes the answer a lot: most current models use grouped-query attention, which has "an intermediate (more than one, less than number of query heads) number of key-value heads".Ainslie et al., "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints" (arXiv 2305.13245). NVIDIA's guide: "Optimizations like MQA and GQA help reduce the memory required by KV caches by reducing the number of key and value heads that are stored." So in the formula, num_heads means the KV heads.

Every number you need is in the model's config.json. Qwen3-32B's says "num_hidden_layers": 64, "num_attention_heads": 64, "num_key_value_heads": 8, "head_dim": 128, "torch_dtype": "bfloat16".Qwen, Qwen3-32B config.json. Its model card: "Number of Attention Heads (GQA): 64 for Q and 8 for KV". Newer hybrid models break the simple formula: Qwen's Qwen3.8-27B lists layer_types, and only 16 of its 64 layers are full_attention with a KV cache. Read the whole config. So, in BF16:

At Torvik's busiest hour, the KV cache is bigger than the BF16 weights. That's normal for a model serving many people. A sizing that only counts the weights is wrong in exactly the situation that matters.

The budget. gpu-01 has two NVIDIA L40S cards, "48GB GDDR6 with ECC" each, with "Fourth-generation Tensor Cores with support for FP8".NVIDIA, "NVIDIA L40S" product page. NVIDIA's CUDA GPUs list gives the L40S compute capability 8.9. vLLM may not use all of it. Its --gpu-memory-utilization is "The fraction of GPU memory to be used for the model executor, which can range from 0 to 1". If you don't set it, it's "1.0 with the extensible KV cache (sized from measured memory) and 0.92 otherwise", and the docs say to "leave this unset unless something needs memory that vLLM does not measure".vLLM, "Engine Arguments", checked November 2026 (latest release v0.34.0). Many guides still say the default is 0.9. It changed. Mats runs GPU monitoring tools on the same cards, so he sets 0.9. vLLM also measures some memory of its own beyond weights and cache (on gpu-01, 2.5 GB per GPU). With two cards: 0.9 × 48 × 2 = 86.4 GB, minus 5 GB.

Making it smaller. Quantization stores the weights, the KV cache, or both, in fewer bits. The evidence says it costs less quality than people fear. One study ran "over 500,000 evaluations" and found that "FP8 (W8A8-FP) is effectively lossless across all model scales", and that INT4 weight-only "is more competitive than expected, rivaling 8-bit quantization".Kurtic et al., "'Give Me BF16 or Give Me Death'? Accuracy-Performance Trade-Offs in LLM Quantization" (arXiv 2411.02355, revised May 2026), on the Llama 3.1 family. AWQ, one INT4 method, "finds that not all weights in an LLM are equally important" (arXiv 2306.00978). vLLM: FP8 gives "a 2x reduction in model memory requirements and up to a 1.6x improvement in throughput with minimal impact on accuracy". It needs the right chip: "FP8 computation is supported on NVIDIA GPUs with compute capability >= 8.9", which includes the L40S.vLLM, "FP8 W8A8". Older cards run FP8 models "as weight-only W8A16". The quantization index lists which method runs on which GPU generation. The KV cache can be FP8 too, which "can significantly reduce its memory footprint". Without a calibration step, "All quantization scales are set to 1.0", so test it like anything else.vLLM, "Quantized KV Cache".

4 · Serving it: every setting on the command line

vLLM "provides an HTTP server that implements OpenAI's Completions API, Chat API, and more", and its own example points the official OpenAI client at base_url="http://localhost:8000/v1".vLLM, "OpenAI-Compatible Server". The same page warns that --api-key doesn't cover every endpoint: "Do not rely on --api-key alone to secure vLLM." On the high side, Lesson 12's NetworkPolicy decides who can reach port 8000. That's why the agent's code barely changes: it calls http://llm.torvik.internal:8000/v1, the address on Lesson 12's egress list. What changes is the command that starts the server. Each memory sum in section 3 is a setting, and anything you don't set takes vLLM's default, not your plan.

Read the start-up log. vLLM tells you what it could fit. One line gives "an estimate of how many requests can be served concurrently if each request requires the specified number of tokens".vLLM, "Parallelism and Scaling", on the log line "Maximum concurrency for 40,960 tokens per request: 15.70x". If even one request doesn't fit, vLLM refuses to start: "To serve at least one request with the model's max seq len (…), (… GiB KV cache is needed, which is larger than the available KV cache memory (… GiB)."vLLM source, vllm/v1/core/kv_cache_planning.py. Note GiB: vLLM counts in 2^30 bytes, while datasheets and file sizes usually count in GB, 10^9 bytes. The opposite case is worse: a server that starts fine and has room for 11 of the 16 conversations. Nothing fails. The other five just wait.

5 · Is it still good? The golden set and the busy hour

Against what? In Lesson 8 you compared a new version of the agent with the one in production. Here, the full-precision model is the reference. It can't serve 16 people on gpu-01, but it can answer the golden set one conversation at a time. Then each smaller version answers the same 12 cases, three times each, through the server exactly as it'll be configured. That means the same flags, so a missing tool parser shows up here and not on the first day of production.

Averages hide the case that matters. The study above reports accuracy averaged over benchmarks. Your customer reads one answer at a time. On Torvik's golden set, the INT4 version scored higher than the reference on average: 33 of 36 runs passed, against 32. But in one run of T-07 it gave the torque for the TR-40's mounting bolts as 2.58 Nm instead of 2.85. Lesson 8's rule catches that: a case that passed every run before and fails any run now is a regression, whatever the average says. A wrong torque on a sonar mount is the kind of mistake Torvik's engineers would act on.

Fast alone isn't fast. Measure speed the way users feel it. "Time to first token (TTFT) measures how long you wait before seeing the model's output", and it "generally includes request queuing time, prefill time, and network latency". Load changes it: "As the number of concurrent requests increases, total system TPS increases while TPS per user decreases as latency increases."NVIDIA NIM, "LLM Inference Benchmarking: Metrics". TPS is tokens per second. So run a load test at Torvik's peak, 16 conversations with long prompts, and read the p95, not the average. Mats tried the FP8 model with a BF16 cache: 0.51 s alone, 6.58 s at 16. vLLM had room for 11 conversations, so the rest queued behind them.

6 · Build it

The exercise lives in exercises/0013-inference/. The top of harness.ts describes gpu-01, Torvik's needs, the four Skerry versions with their config.json fields, the reference grades, and Mats's log of last week's trials. It also has a stand-in for vLLM: it has no GPU and no model, but it starts from your command line using vLLM's rules and messages, then plays back what Torvik measured. You write three functions: fit(), serveCommand() and accept().

start.ts is the sizing most teams do first:

Read check 3 again. The server started. Nothing crashed. It just has room for 1.13 conversations, because the command left the GPU count, the context length and the cache format to vLLM's defaults. That's the failure that reaches production, because a server that refuses to start gets noticed and this one doesn't.

Fix start.ts. The TODO list in the file follows the checks. Give yourself 35 minutes before you open the solution.

  1. KV cache per token: 2 × layers × KV heads × head_dim × bytes (2 for auto, 1 for fp8).
  2. The budget is gpu_memory_utilization of each GPU used. Take off all the weights, and the overhead for each GPU. Then work out how many full-length requests fit in what's left.
  3. Put every setting you sized on the command line.
  4. Serve the folder in the image, and set HF_HUB_OFFLINE=1.
  5. Add the name the agent asks for, and the tool flags with the model card's parser.
  6. Refuse any regression, or any failed request, whatever the average.
  7. Read the p95 at Torvik's peak, and give a reason for every refusal.

Undo that, and delete "--kv-cache-dtype", s.kv_cache_dtype, from the command: only check 3 fails, because the server you sized isn't the server that starts. 7 · May Torvik run it?

Before any sizing, Torvik's lawyers will ask you about each model you put forward. For each card, decide whether you can go ahead, or must stop and get a written answer first. (These are the licences as they read in November 2026. Check again before you rely on them.)

8 · Check yourself

Answer from memory, then read every explanation, including the ones you got right.

9 · Write the sizing memo

Mats runs gpu-01, and Ingrid signs off what runs on the high side. Neither of them was in the room for your tests. Write the memo they'll keep with the system's records: what runs, why it fits, and how to tell when it stops fitting. It saves as you type.

The last check matters most. Numbers that were true in December won't stay true. If Torvik hires twenty more field engineers, or puts a longer manual in the prompt, the busy hour gets bigger and nothing on the server will warn anyone. Put the trigger in the memo, so they know when to run the sums again.
