Forward Deployed Engineering · Lesson 7 · Stage 7 · about 60 minutes

Human-in-the-loop and durable workflows

The agent can now start returns, and a return is money leaving the company. Big ones need a manager's yes, the manager may take two days to give it, and in those two days the server will restart, someone will double-click, and the process will die at the worst moment. This lesson builds a workflow that waits for a real person and still refunds exactly once.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

A returns workflow in Postgres and TypeScript that stops at an approval gate, accepts a decision only from a real returns manager, picks up where it left off after days or after a crash, never creates a return twice (even when the legacy system has no idempotency key), lets only one of two simultaneous runs do the work, and expires on its own when nobody decides in time.

1 · Some actions need a person

An EPAM job ad for an FDE lead puts it in one line: "Design for failure in the agent loop: retries, model fallbacks, cost limits and human-in-the-loop on consequential actions".EPAM's Forward Deployed Engineer job ad, as of November 2026. The MCP specification says the same about tools: "there SHOULD always be a human in the loop with the ability to deny tool invocations".MCP 2026-07-28, "Tools", User Interaction Model. Under "Security Considerations", clients SHOULD also "Prompt for user confirmation on sensitive operations" and "Log tool usage for audit purposes". Anthropic's guide to agents describes agents that "pause for human feedback at checkpoints or when encountering blockers".Anthropic, "Building effective agents", section "Agents".

Here is today's job. At the end of Lesson 5, Acme asked for a tool that starts returns through the order system's CreateReturn. Acme's rule: a return of EUR 500 or more needs a yes from a returns manager first. Today there is one manager, Maria, who approves from a button in a chat app when there's time. That can be minutes or days.

In the EU there is a legal side too. For AI systems the EU AI Act classes as high-risk, Article 14 requires that people can "effectively" oversee them, can "disregard, override or reverse" their output, and can stop them "through a 'stop' button or a similar procedure".EU AI Act, Article 14, "Human Oversight", paragraphs 1 and 4(d) and 4(e). Whether a system is high-risk is a legal question for the customer's lawyers, not for you. A returns tool is probably not high-risk, but the customer's legal team may ask how your design would meet this anyway.

2 · "The user said yes in the chat" is not a gate

The first version most people build lets the agent ask "shall I go ahead?" in the conversation, and calls the reply an approval. For small, reversible actions by the person who asked, that is often fine: it is what a confirmation prompt is for. For Acme's rule it is not, for three reasons:

  • The wrong person. The rule names returns managers. The person chatting with the support agent is a customer or a support colleague, not Maria.
  • The wrong channel. A decision that arrives as text in the conversation can be written by the model itself, or by a prompt injection in an email the agent read. A real gate takes its decision from a place the model can't write to, and checks who made it against a list.
  • No record. Six months later, someone asks who approved a EUR 3,150 return. "The chat said yes" is not an answer. A gate writes the request, the decision, the name and the time to the database.

The request is part of the gate too. Maria decides from what the card says, so it must say what will happen, in numbers: the amount, the order, the customer, the order's total, the reason, and who asked.

3 · A workflow that can wait for days

You can't keep a function running for two days. Servers restart for deploys, and long-running requests time out. So the workflow has to save where it is, stop, and continue later from the saved state, possibly on a different machine. That is a durable workflow. Every serious framework does the same thing in its own words:

Temporal calls a workflow execution "fully recoverable after a failure": "If a failure occurs, the Workflow Execution picks up where the last recorded event occurred in the Event History."Temporal docs, "Workflow Execution", including the section on Replay. A Signal is an "asynchronous write" into a running workflow ("Workflow message passing"). The OpenAI Agents SDK "pauses the run, returns interruptions, and lets you resume later from the same RunState", and for long waits says: "Store serialized state in application-controlled storage, such as a server-side database."OpenAI Agents SDK (JavaScript), "Human in the loop". LangGraph's interrupt "saves the graph state using its persistence layer and waits indefinitely until you resume execution".LangGraph docs, "Interrupts", and "Checkpointers".

At a customer you'll probably use one of these, or whatever they already run. Today you build the core yourself in one short file, because the frameworks all rest on the same four ideas, and when something goes wrong at 2 a.m. you need to know which one broke.

Where MCP fits. An MCP tool call can't stay open for two days. The 2026-07-28 revision moved long-running work into an official tasks extension: "Some operations — CI pipelines, batch processing, human approvals — take seconds, minutes, or longer. MCP Tasks let servers return a durable handle instead of blocking".MCP Tasks extension, overview. For quick questions to the user in the middle of a call, MCP has elicitation: "a standardized way for servers to request additional information from users through the client" (MCP 2026-07-28, "Elicitation"). So the tool starts the workflow and returns a handle at once. The workflow itself lives behind it, in a database.

4 · Idea one: save every step, and replay

Write the workflow as plain code from top to bottom, and wrap each step in a helper. The helper looks in the steps table first. If the step already ran, it returns the saved result. If not, it runs the step and saves the result. Every time run() is called, the code starts again from the top, and finished steps cost nothing. That is replay.

Replay has one rule: the code must take the same path every time it runs. Temporal: "A Workflow Definition must be deterministic to support replay", so API calls, LLM calls and database queries go in Activities, which "execute outside the replay path and are automatically retried".Temporal docs, "Deterministic constraints". In your version, that means anything that can differ between runs goes inside a step, so its saved result is reused: the order lookup, the clock when the request was made, a random id. If the workflow reads now() outside a step to decide which branch to take, a replay can take a different branch than the first run did.

5 · Idea two: the gap between "done" and "saved"

Look at the comment in step() again. CreateReturn succeeds, the process dies before the insert, and on restart the step runs again. Temporal describes exactly this case: "The Activity function completes successfully, but the Worker crashes just before it notifies the Temporal Service." Its answer: "Temporal recommends that Activities be idempotent."Temporal docs, "Activity idempotency". It suggests "a combination of the Workflow Run ID and the Activity ID as an idempotency key". LangGraph says the same about its interrupts, which re-run the node that paused: "side effects called before interrupt should (ideally) be idempotent", so "Place side effects after interrupt calls".LangGraph docs, "Interrupts", section on side effects.

No framework can close this gap for you. A system that retries delivers each step at least once. You get "exactly once" only by making the step safe to repeat. Three ways, best first:

  1. An idempotency key, if the system takes one. With Stripe, "you can safely repeat the request without risk of creating a second object", and "Retries with the same key return the saved response".Stripe API reference, "Idempotent requests". An IETF draft for a standard Idempotency-Key header exists, but it is still an Internet-Draft, not an RFC. Build the key from the workflow id and the step name, so a retry of the same step sends the same key.
  2. Look first, if it doesn't. Acme's CreateReturn has no key, but it stores a free-text reference on each return, and FindReturn looks one up. Write a reference only this step uses, and look for it before you create.
  3. A dedupe key for messages. The notifier drops a second message with the same key. Use the same workflow-plus-step recipe.

"Look first" has a weak spot: two workers can both look, both find nothing, and both create. That is the next idea.

The same gap appears when you save to your database and then send a message: "if a service sends a message after committing the transaction there's no guarantee that it won't crash before sending the message." The transactional outbox pattern stores the message in the same transaction, and a separate process sends it later. Even then, "The Message relay might publish a message more than once", so the receiver still needs a dedupe key.microservices.io, "Pattern: Transactional outbox".

6 · Idea three: one worker at a time

Maria double-clicks Approve. The approval app calls run() twice, a few milliseconds apart. Both calls read the workflow, both see "waiting", both go on. That is a race condition, and checking the status first doesn't fix it, because both checks happen before either run writes anything.

The fix is a claim that only one caller can win, done in one atomic statement. A single SQL UPDATE with a WHERE clause does that: the database lets one of the two updates match the row, and the other finds it already claimed.

The claim is a lease, not a lock: it ends on its own after 30 seconds. If the worker that holds it crashes, nobody has to clean up. The next run() after the lease runs out simply claims it again. The price: a step that takes longer than the lease could overlap with another worker, so keep steps short, or renew the lease as you go. The OpenAI SDK warns about the same trap in its own words: "Concurrent or replayed submissions must not resume the same snapshot twice."

With many workflows waiting, workers usually pick the next one from a queue table. Postgres's FOR UPDATE SKIP LOCKED exists for that: "any selected rows that cannot be immediately locked are skipped", which "can be used to avoid lock contention with multiple consumers accessing a queue-like table".PostgreSQL 19, SELECT, "The Locking Clause".

7 · Idea four: nobody waits forever

Maria goes on holiday. Without a deadline, the customer waits forever and nobody notices. Anthropic recommends "stopping conditions (such as a maximum number of iterations) to maintain control" for agents, and the same goes for a gate.Anthropic, "Building effective agents". Acme's rule: no valid decision within 48 hours, and the request expires. The customer is told nothing was refunded, and a click that arrives later is ignored.

Two details make the deadline reliable. Compute it from the saved request time, not from "now", so every replay gets the same answer. And something has to wake the workflow when the deadline passes, even if nobody clicks. In Temporal that is a durable timer: "even if your Worker or Temporal Service is down when the time period completes", it still fires, and workers "consume no additional resources while waiting".Temporal docs, "Timers". In your version, a scheduled job that calls run() on waiting workflows does the same job.

Now fix start.ts. The TODO list in the file follows the order of the checks. Give yourself 30 minutes before you open the solution.

  1. At EUR 500 or more, write one approval request with a summary Maria can decide from, and return waiting_for_approval. Don't wait inside run().
  2. A "reject" from Maria ends the workflow as rejected.
  3. Count only decisions made by someone in APPROVERS.
  4. Save every step in a steps table with a step() helper. A finished workflow returns its status and does nothing.
  5. Inside the create_return step, look for the return by its reference before creating it. Give every message a dedupe key.
  6. Claim the workflow with an atomic update … returning and a 30-second lease.
  7. After 48 hours with no valid decision: expired, tell the customer, ignore later clicks.

Stuck on check 6, with both runs saying done? Your claim is probably a select followed by an update. Make it one update with the condition in its where clause, and look at whether a row came back.

11 · Design Maria's approval card

Maria will see your approval request as a card in a chat app, between other messages, probably on a phone, and will give it about ten seconds. Write the card for the EUR 1,299 return on order A-1001. It saves as you type.

The last check matters most. If the card says "AI recommends: approve", many people will click approve without reading the rest, and the human in the loop becomes a rubber stamp. Give Maria the facts, and leave the decision to the person.
