Forward Deployed Engineering · Lesson 4 · Stage 4 · about 60 minutes

Permission-filtered retrieval

An enterprise agent searches the customer's documents before it answers. It must only ever find what the person asking may read. This lesson is about where that filter goes, and why "after the search" is the wrong place.

Words with a dotted underline have a plain-English definition. Hover, tap or tab to them. All of them are in the jargon decoder.

Your win today

A search function on real Postgres that returns only the rows the asking user may see, cites every source, and abstains when nothing permitted matches well enough. You'll also be able to explain, in under a minute, why filtering the results after ranking is wrong. That explanation is what a customer's security team wants to hear.

1 · The question every security review asks

Picture the job. You're deploying a support agent for Acme. Your company also runs the same product for Globex, and both customers' documents sit in one shared database: a multi-tenant setup. Inside Acme, support staff may read the refund policy, but not HR's salary bands or finance's fraud review.

RAG makes this harder than in a normal app. The search step decides what the model reads, and the model can repeat anything it reads. So the first question in a customer's security review is: "can the agent ever show my staff a document they couldn't open themselves?"

The OWASP Top 10 for LLM applications lists this risk by name. Its entry on vector and embedding weaknesses warns about "unauthorized access & data leakage", and about cross-context leaks "in multi-tenant environments where multiple classes of users or applications share the same vector database". Its fixes are "permission-aware vector and embedding stores" and "strict logical and access partitioning of datasets".OWASP, "LLM08:2025 Vector and Embedding Weaknesses". Its neighbour, LLM02:2025 Sensitive Information Disclosure, adds: "Only grant access to data that is necessary for the specific user or process."

So there are two walls to build, and they are different:

  • Tenant isolation: an Acme user never touches a Globex row. One wrong row here can end the contract.
  • Document access: inside Acme, each document has an ACL, a list of the groups allowed to read it. Alice in support reads what everyone and support may read, and nothing else.

2 · Filter before you rank, not after

The tempting design is the one most RAG tutorials show: search everything, take the top-k best matches, then drop the ones the user may not see. This is called post-filtering. It fails in two separate ways.

It leaks. The forbidden rows have already left the database. They are now in your process, and anything that touches them before the filter runs holds data the user may not see: a debug log of "what we retrieved", a trace in your telemetry, a cache, an eval dataset built from logs, or the prompt itself if someone filters in the wrong place. Each of these is one small mistake away from a leak, and none of them shows up in a demo.

It starves. If the top-k slots are filled by documents the user can't see, the filter leaves few or none. The user gets "no results" while a perfectly good permitted document sat in sixth place. The pgvector docs state this plainly for vector search: "With approximate indexes, filtering is applied after the index is scanned. If a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average."pgvector README, "Filtering". Since version 0.8.0, "iterative index scans" scan more of the index until enough rows pass the filter. The same README says: "For tenant isolation, use list partitioning or separate tables." A user who may read 10% of the documents gets 4 results instead of 40. A user who may read 1% often gets none.

Post-filtering (rank, then filter in app code)Pre-filtering (filter in the query that ranks)
Forbidden rows leave the database?Yes, every one that ranked in the top-kNever
Results for a user with narrow accessFew or none, even when good matches existThe best k among the rows they may see
Where the rule livesIn every caller that remembers to apply itIn the database, next to the data

The fix is to put the permission check inside the same query that ranks. SQL reads WHERE (and row-level security, below) before ORDER BY and LIMIT, so forbidden rows never compete for a top slot and never come back.

3 · Put the rule in the database with row-level security

Lesson 3 taught row-level security: default deny, table owners and superusers skipping it, and a transaction-local setting that tells the policy who is asking. Retrieval adds nothing new to that machinery. It just raises the stakes, because whatever the search returns goes straight into a prompt. Two reminders matter most here:Both from PostgreSQL docs, "Row Security Policies".

  • The filter is silent. "Rows for which the expression does not return true will not be processed." There is no error. The search just sees fewer rows, which is exactly what you want for ranking.
  • Owners skip it. "Table owners normally bypass row security as well." If your search runs as the role that created the table, your policy does nothing, and every check still looks fine in a demo where you are an admin.

Supabase's guide to RAG with permissions uses the same pattern as Lesson 3: "a custom session variable that contains the current user's ID", read in the policy with current_setting().Supabase, "RAG with Permissions", section on connecting to Postgres directly. Here the policy needs two facts, the tenant and the user's groups, so the exercise sets two settings. Both are set with set_config(name, value, true), which applies "only during the current transaction", so a pooled connection can't carry one user's groups into the next request.PostgreSQL docs, "System Administration Functions". SET LOCAL ROLE works the same way: LOCAL lasts "only till the end of the current transaction, whether committed or not" ("SET"). As in Lesson 3, the values come from the token your server verified, never from anything the model wrote.

acl && groups means "the two arrays share at least one item". The true in current_setting(name, true) returns NULL instead of an error when the setting is missing.current_setting "throws an error unless missing_ok is supplied and is true (in which case NULL is returned)". PostgreSQL docs. NULL is never true, so a request that forgets to say who is asking gets zero rows. The policy fails closed.

RLS or an explicit WHERE? Both filter before ranking, so both pass this lesson's checks. An explicit WHERE tenant = $1 AND acl && $2 is simpler and easy to read in a code review, but every query, including the one a teammate writes next year, must remember it. RLS can't be forgotten: Supabase recommends it because it "is always applied even as new queries and application logic is introduced in the future". The costs: every request needs a role and settings inside a transaction, a mistake shows up as silently empty results rather than an error, and Supabase warns that RLS is sensitive to latency when permissions come from another system. On a customer deployment with several engineers touching the code, RLS is usually the safer default.

4 · Ranking: keywords now, vectors later

The exercise ranks with Postgres full-text search, because PGlite runs real Postgres in-process with no setup but doesn't bundle pgvector, and real embeddings would need an API key. Three pieces do the work:PostgreSQL docs, "Controlling Text Search". plainto_tsquery puts an AND between the words; the exercise swaps it for OR so partial matches get a low score instead of no score.

  • a tsvector column, generated from each document's title and body, holding its words in normalised form ("refunds" becomes refund);
  • plainto_tsquery('english', 'refund policy'), which turns the user's text into a query;
  • ts_rank(tsv, q), which "ranks vectors based on the frequency of their matching lexemes" (lexemes are those normalised words).

A ts_rank score has no fixed scale. The docs say the ranking functions "do not use any global information, so it is impossible to produce a fair normalization to 1% or 100%". So the abstention threshold in the exercise (0.05) is tuned on this corpus. On a customer's data you tune it again, ideally with an eval.

Swapping in vectors changes the ranking line, not the permission. With pgvector you would store an embedding per chunk and order by distance to the query's embedding instead of by ts_rank. The policy is identical, because RLS works on rows and doesn't care how they are scored. Supabase's guide does exactly this: the same kind of policy, on a table of document chunks with a pgvector column.

Hybrid search runs both and merges them. Anthropic's Contextual Retrieval post explains why: "embedding models excel at capturing semantic relationships, they can miss crucial exact matches", such as an error code like TS-999. Keyword ranking (BM25) finds the exact string. Combining contextual embeddings with contextual BM25 cut their top-20 retrieval failure rate by 49%, and adding a reranker took it to 67%.Anthropic, "Introducing Contextual Retrieval", September 2024. The results are merged "using rank fusion techniques". Postgres's built-in ts_rank is a simpler frequency score, not BM25. For permissions, the rule is simple: both halves must be filtered. With RLS on the table, both queries are filtered without anyone remembering to.

5 · Citations and abstention

Citations. Return each hit's id and title with its score, and show them with the answer. A person can check the answer against the source, and your logs record exactly which rows the model saw. A passage with no source can't be checked, and can't be traced back if it turns out to be one the user shouldn't have seen.

Abstention. If no permitted document clears the threshold, say so: "I couldn't find a document you have access to that answers this." Don't hand the model a weak match and hope. And don't say "there's an HR document about this, but you can't open it": that tells the user the document exists, which is itself a leak. With RLS you couldn't say it anyway, because the app never learns the forbidden rows were there.

6 · GraphRAG, in one paragraph

The roadmap names this stage "Permission-filtered RAG & GraphRAG". Microsoft's GraphRAG builds an index by "extracting a knowledge graph out of raw text", then groups related entities into a "community hierarchy" and writes summaries for each community. It targets questions where "baseline RAG struggles to connect the dots" across many documents.Microsoft, GraphRAG project page. You won't build one here. But carry one question into any GraphRAG project: a community summary is written from many documents, so who may read it? If even one of its sources is restricted, the summary needs that restriction too.

Read the third line closely. Alice may read Acme's refund policy, yet the naive search abstained: Globex's two refund documents and Acme's finance review took all three top slots, then the filter threw them away. That's starvation. And the fourth line is the opposite mistake: with no threshold, a weak match on the word "salary" (the payroll FAQ) comes back as if it answered "salary bands".

Now write search(user, query) in start.ts. Give yourself 30 minutes before you open the solution.

  1. Filter by tenant and groups inside the database. Either enable RLS and write a policy, then run each search in a transaction as app_user with the settings made local. Or add an explicit WHERE to the ranking query. Try RLS first.
  2. Select id and title with the score, so every hit is citable.
  3. Drop hits below MIN_SCORE. If nothing is left, abstain.

Stuck on RLS returning every row? You're probably still the superuser that owns the table. Check that set local role app_user ran inside the same transaction as the query.
